# Keyway 竞品审视

日期: 2026-09-25

## 对比对象

### LiteLLM

官网当前把重点放在平台团队:统一 API、140+ provider、预算/限流、可观测性、路由和治理,并强调可自托管。它解决的是组织级模型基础设施问题,不是桌面端 CLI 配置管理。

### Portkey / PRISMA AIRS AI Gateway

官网当前把重点放在企业生产控制面:统一接入、观测、Guardrails、MCP、RBAC、成本治理和审计。它的优势是团队治理与云端控制面,同时也意味着更重的部署和组织协作语境。

### CC Switch

GitHub README 将其定位为多 CLI 的本地一体化管理器,覆盖 Claude Code、Claude Desktop、Codex、Gemini CLI、OpenCode、OpenClaw 等,并提供配置切换、接管与生态入口。它是 Keyway 更直接的本地竞品,优势是覆盖面和社区声量。

## Keyway 的取舍

Keyway 不应复制 LiteLLM/Portkey 的企业控制面,也不应在官网上与 CC Switch 比“支持数量”。更清晰的差异是:

- 本地代理优先:控制面、密钥和接管状态留在本机,不把 Keyway 包装成托管 API 中转站。
- 状态可验证:明确区分代理运行、CLI 接管和请求实际成功,用请求日志证明最终去向。
- 改动可撤销:接管前备份,还原时检测冲突,避免静默覆盖用户后续修改。
- 配置而非销售:供应商由用户选择,Keyway 不绑定单一模型或中转服务。

## 本轮落实

- 官网主截图重新生成,反映当前“供应商管理 + 模型路由试算 + 网关详情入口”的产品界面。
- 首页新增“本地优先”请求路径,用 CLI → 本机代理 → 用户供应商解释边界。
- 首页能力文案补充“先预览路由”和“实际供应商”,避免把默认供应商误写成真实去向。
- 首页保留准确限制说明:请求内容仍会发送给用户选定的上游,本地存储不等于离线推理。

## 后续建议

优先级最高的产品补强不是继续堆供应商数量,而是让首次用户更快完成闭环:

1. 首次接管后的验证向导:检查代理、接管状态,引导发出一条请求并自动跳到日志。
2. 更明确的供应商健康状态:区分连接失败、鉴权失败、限流和代理离线,给出下一步动作。
3. 可选的成本/预算视图:先做本地估算和按 CLI/供应商聚合,不要引入托管账单或强制云端账户。
4. 继续扩大 CLI 覆盖前,先补齐每个 CLI 的接管说明、手动环境变量和安全还原路径。
