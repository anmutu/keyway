Switching AI providers: the three things you must change

Blog · Series · Part 1 · 2026-11-06 · ~5 min · author

The 30-second answer:you touch three things — ① the Base URL, written into the CLI's config file; ② the API key, usually stored as an environment variable; ③ the pointer that tells the CLI to actually use it, followed by a fresh session. The only difference between operating systems is which directory the file lives in and how env vars are persisted.

1. First, see the path: the journey of one request

Codex, Claude Code or Gemini CLI — before configuring anything, know where your edits sit in the path:

You hit Enter
   │
   ▼
The AI CLI process (it finished reading its config the moment it started)
   │   ① Base URL   ──── which server requests go to
   │   ② API key    ──── what identity requests carry
   │   ③ model name / parameters
   ▼
HTTPS request (address = Base URL + path; auth = the key in a header)
   │
   ▼
Upstream server (official or third-party)
   │
   ▼
Streaming response ──► the CLI renders it in your terminal

Every "switch provider" action is, at its core, changing the Base URL and the API key at the top of this diagram. A third thing usually follows: the model name, because the same model is often named differently by different providers — reusing the old name tends to fail with "model not found". Everything else the CLI does — conversation, tool calls, context — has nothing to do with provider config; you don't touch a line of it.

2. Three concepts you must understand

① Base URL — the street address

Every official CLI ships with an official address; switching to a third-party provider means replacing it with the URL they give you, e.g. https://api.example.com/v1. Mind the /v1: some providers include it, some require you to add it — their docs are the source of truth. A wrong path typically shows up as a 404.

② API key — the ID card

Generated in the provider's console, shaped like sk-xxxx…. The CLI puts it into the Authorization header. A key is bound to the provider that issued it: provider A's key is a dead card at provider B. Where it usually lives:an environment variable (per-OS details below).

③ Protocol — three dialects

Anthropic, OpenAI and Gemini are three different wire protocols. Claude Code only speaks Anthropic-compatible, Codex only OpenAI-compatible, Gemini CLI only the Gemini format — they are not interchangeable. When a third-party provider advertises "OpenAI-compatible", it means they accept every CLI that speaks that dialect. Check the protocol matches before buying a key (providers usually state which protocols they support).

3. macOS / Windows / Linux: where to go

CLI configs hide in your home directory:

Home directoryCodex config (example)
macOS/Users/you/ (~ in a terminal)~/.codex/config.toml
WindowsC:\Users\you\ (type %USERPROFILE% in Explorer's address bar)%USERPROFILE%\.codex\config.toml
Linux/home/you/ (also ~)~/.codex/config.toml

Environment variables: each OS persists them differently

To persistTo apply right now
macOSadd export MY_KEY="sk-xxx" to ~/.zshrcsource ~/.zshrc, or open a new terminal window
Windowsin PowerShell: setx MY_KEY "sk-xxx" (writes the user variable)open a new PowerShell window — setx never affects the current one
Linuxadd export MY_KEY="sk-xxx" to ~/.bashrc (or ~/.zshrc)source ~/.bashrc, or open a new terminal

The shared trap:a CLI process reads env vars and config files exactly once, at startup. A running CLI never learns about your edits — new terminal window → new CLI session is the standard closing move of every manual configuration.

4. How do you know it worked? The three universal checks

  1. Is the variable there?echo $MY_KEY (macOS/Linux) or echo $env:MY_KEY (Windows PowerShell). It only counts if the key prints.
  2. Is the address reachable and the key valid?Send one minimal request (OpenAI-compatible example): 
    curl https://api.example.com/v1/models \
  -H "Authorization: Bearer $MY_KEY"
    A JSON model list means both are good. 401 = wrong key; 404 = wrong path (usually /v1); timeout = network.
  3. In the CLI:open a new session and ask anything — a normal streaming reply means the path is complete.

5. The ceiling of the manual approach

One configuration isn't hard. The pain is repetition: switching again means the whole ritual again; bouncing between two providers means editing files back and forth and remembering to restart sessions; one typo produces errors that aren't always obvious. That is the fate of every "edit the file" approach — files have no memory and no concept of "switching".

This series walks through each CLI's manual setup in full before discussing how to make the pain disappear. Next up: Codex, hands on the keyboard.

FAQ

Why didn't my change take effect?

CLIs read config and environment once at process startup. Open a new terminal window and a new CLI session.

Is a key safe on my machine?

Local env vars and config files are readable only by someone who can log into your machine. The real risks: screenshots, uploads, and committing key-bearing files into git.

To /v1 or not to /v1?

Follow the provider's docs. Rule of thumb: official OpenAI URLs include /v1; many third-party providers accept both. Suspect it first when you see a 404.

Can keys be shared across providers?

Across providers: never. A key is bound to the service that issued it — an OpenAI key at an Anthropic endpoint is an invalid string (401). But one third-party key can serve that provider's multiple protocol endpoints: the protocol belongs to the endpoint, not the key.
