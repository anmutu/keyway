Claude Code, by hand: settings.json vs environment variables

Blog · Series · Part 3 · 2026-11-06 · ~6 min · author

The 30-second answer:switching Claude Code's provider = editing the env block in ~/.claude/settings.json: set ANTHROPIC_BASE_URL (where requests go) plus ANTHROPIC_AUTH_TOKEN or ANTHROPIC_API_KEY (the identity), save, then open a new session. One extra trap vs Codex: the same settings can live in two places — the config file and your shell. Keep exactly one.

1. Claude Code's config map

PlaceWhat it ownsTouched today?
~/.claude/settings.jsonUser-level settings; its env block can set environment variables — the recommended home for manual provider config.✅ main
Shell env varsExporting the same names in .zshrc / .bashrc / setx works equally well.⚠️ pick one of the two
~/.claude.json(login state)Claude Code's own runtime state, including official subscription login.❌ don't hand-edit

Why settings.json is recommended:it's a plain JSON file — backup-able, diffable, movable to a new machine in one piece. Variables scattered across shell configs are invisible; three months later even you won't remember what you set.

2. Hands on: four steps

Step 1 · Back up and open settings.json

macOSLinux

cp ~/.claude/settings.json ~/.claude/settings.json.bak
nano ~/.claude/settings.json   # macOS alternative: open -e

Windows(PowerShell)

copy $env:USERPROFILE\.claude\settings.json $env:USERPROFILE\.claude\settings.json.bak
notepad $env:USERPROFILE\.claude\settings.json

Step 2 · Write the env block (copy-ready)

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.example.com",
    "ANTHROPIC_AUTH_TOKEN": "sk-your-key"
  }
}
  • ANTHROPIC_BASE_URL: the provider's Anthropic-compatible endpoint.
  • ANTHROPIC_AUTH_TOKEN: sent as a Bearer token — the most common style for third-party endpoints. ANTHROPIC_API_KEY instead uses the x-api-key header (official API style) — pick per your provider's docs; usually just one.
  • Other settings already in the file (like permissions)? Keep them; only add/edit the env block.

Step 3 · Remove the same variables from your shell (avoid the fight)

If you exported these variables before, both places now define them and behavior depends on load order — miserable to debug. Check and clean:

# macOS / Linux: any leftovers in shell configs?
grep -n "ANTHROPIC" ~/.zshrc ~/.bashrc 2>/dev/null

# Windows PowerShell: any in the current environment?
Get-ChildItem env: | Where-Object Name -like "ANTHROPIC*"

Delete leftover lines (or Remove-Item Env:ANTHROPIC_xxx for the current window) so the single source of truth is settings.json.

Step 4 · New session, verify

  1. New terminal window → new Claude Code session;
  2. Ask anything — a normal reply means the path works;
  3. To isolate problems, curl the upstream directly: 
    curl https://api.example.com/v1/messages \
  -H "x-api-key: sk-your-key" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model":"claude-3-5-haiku-latest","max_tokens":16,"messages":[{"role":"user","content":"hi"}]}'
    Normal JSON = address and key both good. 401 = wrong key or wrong auth variable (try the other one); 404 = wrong path.

4. Switching cost: the same fate as Codex

Back to official, to a second provider, back again — each round is "edit file → new session", with subscription login and API mode interleaving (subscription login needs no env vars at all; setting BASE_URL switches you to the custom endpoint). Manually herding three CLIs' configs turns your machine into a treasure map. Next: Gemini CLI — its trap is the most interesting: config lives in a .env file that is read only when the process starts.

FAQ

Do subscription (Claude Pro/Max) and these settings conflict?

With subscription login, Claude Code uses official OAuth and needs none of these variables; once ANTHROPIC_BASE_URL is set, requests go to your endpoint instead. Two different modes — don't mix them at once.

Project vs user settings?

A project can carry its own .claude/settings.json, merged with the user-level one. Per-project providers are possible but juggling merge results manually gets confusing fast — beginners should stick to the user level.

Is the key safe inside settings.json?

Same exposure as shell configs (locally readable). Same rules: no git, no screenshots — and the .bak backup contains the key too, treat it the same.
