Codex, by hand: your provider lives in config.toml

Blog · Series · Part 2 · 2026-11-06 · ~7 min · author

The 30-second answer:all of Codex's provider config lives in ~/.codex/config.toml: write a [model_providers.name] block with the base URL, put the key in the environment variable named by env_key, point the top-level model_provider at the block, then open a new terminal and a new codex session. Editing the file without restarting the session changes nothing.

1. Codex's path: decided at startup

codex session starts
   │
   │ reads ~/.codex/config.toml (exactly once!)
   │    model_provider = "myrelay"        ← which provider is active
   │    [model_providers.myrelay]
   │       base_url = "https://…"          ← where requests go
   │       env_key  = "MYRELAY_API_KEY"    ← the env var holding the key
   │
   │ reads MYRELAY_API_KEY from the environment
   ▼
HTTPS request ──► the provider at base_url ──► streaming reply

Once this diagram clicks, the rest stops being "copy these commands" and becomes "I know which link of the chain I'm editing".

2. Know the doors: where Codex keeps its config

Before touching anything, look at the whole map. There are exactly three roles, and today we only touch one:

File / placeWhat it ownsTouched today?
~/.codex/config.tomlMain config: provider list, active provider, model, approval policy. The battlefield.✅ only this
~/.codex/auth.jsonOpenAI official login credentials (subscription mode). Not needed for custom providers.❌ leave it alone
Environment variablesWhere API keys live, referenced by name via the env_key field.✅ step 3

Two preemptive notes:

  • config.toml usually holds more than providers — model choice, safety policy, etc. This guide only adds/edits provider lines and leaves everything else untouched; back up first (step 1 does).
  • If the file doesn't exist, you simply haven't customized anything yet — step 1 creates it and Codex reads it as usual.

On Windows, replace ~ with %USERPROFILE% (C:\Users\you); everything else is identical.

3. Hands on: five steps (macOS as the base, OS deltas marked)

Step 1 · Find (or create) the config file

macOSopen Terminal and run:

mkdir -p ~/.codex
nano ~/.codex/config.toml     # or: open -e for TextEdit

Windowsopen PowerShell:

mkdir $env:USERPROFILE\.codex -Force
notepad $env:USERPROFILE\.codex\config.toml

Linuxis identical to macOS (nano ~/.codex/config.toml).

If the file already exists, edit it — and copy a backup first (the manual approach's life insurance):

cp ~/.codex/config.toml ~/.codex/config.toml.bak

Step 2 · Write the provider block (copy-ready, change two lines)

# Top level: which provider is active (points at the block below)
model_provider = "myrelay"

[model_providers.myrelay]
name = "My Provider"                      # display name, anything you like
base_url = "https://api.myrelay.com/v1"   # ← the URL your provider gave you
env_key = "MYRELAY_API_KEY"               # which env var holds the key
wire_api = "responses"                    # protocol: responses (new) or chat (classic)

Line by line:

  • model_provider: the top-level switch. When you add a second provider later, this is the line you flip — remember it for the switching-cost section.
  • base_url: the endpoint from the provider's docs. Whether /v1 is included follows their docs; Codex appends the API path after it.
  • env_key: a variable name, never the key itself. By design — keys stay out of config files and out of git.
  • wire_api: whichever the provider supports (their docs say). A wrong pick typically means 404 or parameter errors.

Step 3 · Put the key into an environment variable

macOS(zsh, the default):

echo 'export MYRELAY_API_KEY="sk-your-key"' >> ~/.zshrc
source ~/.zshrc

Linux(bash):

echo 'export MYRELAY_API_KEY="sk-your-key"' >> ~/.bashrc
source ~/.bashrc

Windows(PowerShell — setx writes the user variable permanently):

setx MYRELAY_API_KEY "sk-your-key"
# note: setx never affects the current window — close it and open a new one

Step 4 · New terminal, new session

This is where 90% of "nothing changed" failures happen: codex reads its config and environment exactly once at process startup. The correct move: close the current terminal window → open a new one (loads the new variable) → start a new codex session.

Step 5 · Verify

  1. Variable present?echo $MYRELAY_API_KEY (Windows: echo $env:MYRELAY_API_KEY) — it only counts if it prints.
  2. Upstream reachable?(optional) 
    curl https://api.myrelay.com/v1/models \
  -H "Authorization: Bearer $MYRELAY_API_KEY"
    A JSON model list means address and key are both right. 401 = key problem; 404 = path problem (suspect /v1 first). Some providers don't expose a models endpoint — a 404 here with step 3 passing still counts as success.
  3. The real thing:ask anything in the new codex session — a normal streaming reply means the whole path works.

4. Error lookup table

SymptomMost likely causeFix
Nothing changedold session still running / variable not loadednew terminal window + new codex session
401 Unauthorizedwrong key, not exported, or name ≠ env_keyecho the variable; check env_key spelling
404 Not Foundwrong base_url path / wrong wire_apitoggle /v1; match wire_api to the provider's docs
Connection timeoutnetwork down or provider outagecurl the upstream directly; try another network
Model not foundmodel name this provider doesn't carryuse a name from their model list

5. A second provider? Back and forth? The real cost

Adding one more provider: repeat step 2 with a new block and one more env var — that part is one-time. Expensive is every switch:

switch = open config.toml
        → edit the top-level model_provider line
        → save
        → close the terminal window
        → open a new window
        → start a new codex session
        → (maybe retry the question you were in the middle of)

Once a day it's a ritual; several times an hour it's torture — and "this provider is rate-limited, use that one" or "route this model officially, that one via a third party" is precisely the daily reality of heavy users. Config files can't solve this, because they have no memory and no concept of "switching". That's why manager tools exist — but first, Claude Code and Gemini CLI deserve the same manual walkthrough, so you get the complete picture of the pain. Next article.

FAQ

What is auth.json? Does it conflict?

~/.codex/auth.json stores OpenAI official login credentials (subscription mode); custom providers go through config.toml + env vars. The two mechanisms don't interfere.

Is a plaintext key in .zshrc / .bashrc safe?

Same local exposure as config.toml. The risks are syncing dotfiles into public repos and screenshots. Never commit keys to git.

Can two providers be "online" at once?

Blocks can coexist, but the top-level model_provider has a single current value; switching means editing the file and restarting the session.

Is there a way to avoid editing files every time?

Yes — later in this series we'll cover how manager tools work (local-proxy takeover). If you're in a hurry, the Keyway guide is here.
