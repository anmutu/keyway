The three-CLI config cheat sheet, and how manager tools work

The 30-second answer:everything manual fits in one table; and the core idea of local-proxy tools is a single sentence — lock the CLI to a proxy on 127.0.0.1, so "switching providers" goes from editing config files to changing one setting of the proxy. That's why switching stops needing restarts.

Three formats, three sets of key names, three read timings — that's the entire complexity of manual management, and the entire reason it breaks.

2. The switching bill: six manual steps vs the one click you expected

manual: open file → edit URL/key lines → save → close terminal → open new → new session
expected: I want the other provider — click

Part 5 explained why CLIs must "decide at startup" — not a bug, a stability choice. Is the conflict unsolvable? One structure dissolves it: give the CLI a world with exactly one, never-changing address.

3. How the local proxy works: one diagram

[manual]                             [proxy]
                                      CLI ──► 127.0.0.1:9527 (local proxy)
CLI ──► provider A  ← switch = edit+restart      │  proxy checks the current selection
                                           ├──► provider A (official)
CLI ──► provider B  ← again = edit+restart       ├──► provider B (third-party)
                                           └──► provider C (backup / failover)

Four steps:

  1. Takeover:the tool rewrites the endpoint in the CLI's config to the local proxy (backing up the original first). As far as the CLI knows, the proxy is its provider.
  2. Key custody:each provider's key goes into the tool's local encrypted store; the CLI never holds real keys, and the proxy injects credentials per the current selection when forwarding.
  3. Switching:you pick another provider → only the proxy's forwarding target changes, the config file doesn't move → sessions already routed through the proxy send their next request to the new provider, no restart.
  4. Restore:done with it? One click puts the config back from the backup — the CLI returns to direct connection as if nothing happened.

Free bonuses: the proxy sees the actual destination of every request (you selected A, but a routing rule or failover sent you to B — the log says so), plus token usage stats. Observability manual configuration can never give you.

4. Honest boundaries (Keyway as the example)

  • the tool must stay running while the proxy is in use (tray-resident is fine); fully quitting stops forwarding;
  • after the first Codex takeover you need one new session (later switches don't);
  • "local" means the control plane is local: request content and credentials still go to the upstream provider you choose — identical to the manual data flow; keys are never uploaded to any third-party server (SQLCipher-encrypted on device, master key in the OS keychain);
  • in-flight requests are never migrated; switching affects subsequent requests.

And that's the series. You now hold the complete manual picture for all three CLIs — and you know that "one-click switching" isn't magic, just a clever, restrained middleman.

FAQ

Does the proxy slow requests down?

The path becomes "local machine → upstream"; the only addition is one hop inside your own machine, typically sub-millisecond. The real latency always lives on the provider's side.

What happens to my CLI if the tool crashes?

The CLI can't reach "its provider" (the proxy is gone) and reports connection errors. The config file is still there — one-click restore (or manually pasting the backup value) returns it to direct connection, which is exactly why takeover must back things up.

Is this the same as editing hosts or using a system proxy?

No. A system proxy affects the whole machine's traffic; this kind of tool takes over a single CLI's API address — finer-grained and non-interfering.
