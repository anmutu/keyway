"Changed the config, nothing happened" — how AI CLIs load settings

Blog · Series · Part 5 · 2026-11-06 · ~5 min · author

The 30-second answer:because everything was read in the past — shell config runs when the window opens, environment variables are snapshotted when the CLI process starts, config files are read once at startup. You edit the present; the program sees the world as it was at birth. New window + new process is the universal fix.

1. One timeline says it all

Yesterday                       Today
  │                              │
  ▼                              ▼
terminal window opened           you edit .zshrc / setx / config.toml
  │                              │
  ▼                              ▼
shell ran .zshrc ──► env ready   (these changes affect nothing that exists)
  │
  ▼
CLI process started: env snapshot + config read ──► never read again
  │
  ▼
you edit files today, same window ──► the running CLI knows nothing

Three snapshot layers stack: the window layer (shell config), the process layer (env vars), the application layer (config files). A change in any layer must re-run everything downstream of it.

2. Refresh rules per OS

What you changedmacOS / LinuxWindows
var in shell configsource ~/.zshrc or new window—(see next row)
user env var (setx)—must open a new PowerShell/CMD window; $env:NAME=value for the current one
CLI config filenew CLI session (same for all three CLIs)
IDE integrated terminalinherits the IDE's environment — restart the whole IDE; a new tab doesn't help

3. The five-step diagnostic (in order, stop when one hits)

  1. In the same window, print the variable: echo $MY_KEY (macOS/Linux) / echo $env:MY_KEY (Windows).
    Doesn't print → window layer: wrong place, or an old window.
  2. Single definition? Grep your shell config + check the CLI's own file; the same name in both → delete one (single-source-of-truth).
  3. Is the process new? Was the current session started before your edit? Restart it.
  4. Is the file valid? A JSON/TOML syntax error can void the whole file — run it through a validator; check .env for stray quotes/spaces.
  5. Bypass the CLI: curl the upstream directly with the address and key (commands in earlier parts). curl works but CLI doesn't → CLI config; curl fails too → provider or network.

4. Why do these tools read "only once"?

Not laziness — stability. If configuration could change mid-session, two requests from one conversation might land on different providers, and billing, context and debugging would all unravel. "Decided at startup" is a deliberate engineering choice shared by all these CLIs. The conflict is human:people want to switch on a whim; configuration is inherently frozen. That conflict is the protagonist of the final article.

FAQ

Still broken after source?

Confirm the file your shell actually loads: macOS defaults to zsh and ~/.zshrc, but oh-my-zsh or a changed shell alters this. echo $SHELL first.

Is there a way to make changes instant?

Not for a running session (see section 4). Getting close requires a local-proxy style setup — the next article explains how it works.

What about CI and servers?

CI starts fresh processes every run, so no stale snapshots — the real trap there is keys leaking into logs or repos. Long-running services on servers: same rule, restart after .env changes.
