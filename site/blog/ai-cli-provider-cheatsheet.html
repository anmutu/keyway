三家 CLI 配置对照总表,以及管理工具的原理

博客 · 系列 · 第 6 篇(收官)· 2026-11-06 · 约 7 分钟 · 作者

30 秒答案:手动方案的全部细节一张表装下;而"本地代理"类工具的核心思路只有一句话——把 CLI 锁定到 127.0.0.1 上的一个代理,让"换供应商"从改配置文件变成改代理的一格选择,于是切换不再需要重启会话。

一、手动配置对照总表(收藏向)

CodexClaude CodeGemini CLI
配置文件~/.codex/config.toml~/.claude/settings.json~/.gemini/.env
地址写在哪[model_providers.x] base_urlenv.ANTHROPIC_BASE_URLGOOGLE_GEMINI_BASE_URL
Key 放哪env_key 指定的环境变量ANTHROPIC_AUTH_TOKEN 或 ANTHROPIC_API_KEYGEMINI_API_KEY(配合 /auth 切认证)
启用哪家顶层 model_provider—(地址即指向)—(地址即指向)
读取时机进程启动会话启动进程启动(只读一次 .env)
Windows 路径%USERPROFILE%\.codex\%USERPROFILE%\.claude\%USERPROFILE%\.gemini\
格式雷区TOML 语法、wire_api 选错JSON 逗号、两处定义打架引号/export 多余、OAuth 未切

三家三种格式、三套键名、三种读取时机——这就是手动管理的全部复杂度,也是它容易出错的全部原因。

二、切换的账:手动六步 vs 心里的预期一步

手动:打开文件 → 改地址/Key 行 → 保存 → 关终端 → 开新终端 → 新开会话
预期:我想用另一家,点一下就完

第 5 篇解释了为什么 CLI 必须"启动时定案"——这不是 bug,是工程上的稳定选择。矛盾无解了吗?有一种结构恰好化解它:让 CLI 的世界里只有一个永远不变的地址。

三、"本地代理"的原理:一图看懂

【手动模式】                          【代理模式】
                                      CLI ──► 127.0.0.1:9527(本地代理)
CLI ──► 供应商 A  ← 换家 = 改文件重启            │  代理查一眼"当前选择"
                                           ├──► 供应商 A(官方)
CLI ──► 供应商 B  ← 再换 = 再改再重启            ├──► 供应商 B(第三方)
                                           └──► 供应商 C(备用,故障转移)

分四步拆开:

  1. 接管:工具把 CLI 配置里的接口地址改写为本地代理(改前自动备份原文件)。对 CLI 来说,代理就是"我的供应商"。
  2. Key 托管:各家的 Key 存进工具的本机加密库;CLI 手里不再有真实 Key,代理转发时按当前选择注入认证。
  3. 切换:你点选另一家 → 只有代理内部的转发目标变了,配置文件一动不动 → 正在通过代理的会话,下一个请求就走新家,不用重启。
  4. 还原:不想用了,一键把配置从备份恢复,CLI 回到直连,仿佛一切没发生过。

顺带的收益:代理能看到每个请求的实际去向(默认选了 A,但路由规则/故障转移把你送去 B,日志里一目了然),还能顺手统计 token 用量——这些是手动配置永远给不了的观测能力。

四、诚实的边界(以 Keyway 为例)

  • 代理运行期间工具需保持开启(托盘驻留即可),完全退出会停止转发;
  • 首次接管 Codex 后需要新开一次会话(此后切换不再需要);
  • "本地"指控制面在本机:请求内容与认证仍会发给你选择的上游供应商,与手动配置时的数据流向完全一致;Key 不上传任何第三方服务器(SQLCipher 加密存本机,主密钥在系统钥匙串);
  • 已发出/进行中的请求不会被迁移,切换影响的是后续请求。

常见问题

代理会不会拖慢请求?

转发路径是"本机 → 上游",多出的只有本机进程内的一跳,通常在毫秒级;真正的延迟大头永远在供应商侧。

工具崩了我的 CLI 会怎样?

CLI 会连不上"供应商"(代理不在了),报连接错误;配置文件仍在,一键还原(或手动把地址改回备份值)即恢复直连——这也是接管必须做备份的原因。

和直接改 hosts / 用系统代理是一回事吗?

不是。系统代理影响整机流量;这类工具只接管单个 CLI 的 API 地址,粒度更细、互不干扰。
