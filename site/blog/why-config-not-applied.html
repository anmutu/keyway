为什么"改了配置没生效"?配置加载顺序详解

博客 · 系列 · 第 5 篇 · 2026-11-06 · 约 6 分钟 · 作者

30 秒答案:因为配置和变量的读取都发生在过去——shell 配置文件在窗口打开时执行,环境变量在CLI 进程启动时被快照,配置文件同样只在启动时读一次。你改的是现在,程序看的是它出生那刻的世界。新窗口 + 新进程是万能解。

一、一张时间轴看懂

你昨天                     你今天
  │                          │
  ▼                          ▼
打开终端窗口                修改 .zshrc / setx / config.toml
  │                          │
  ▼                          ▼
shell 执行 .zshrc ──► 环境就绪    (这些变化不影响任何已存在的东西)
  │
  ▼
启动 CLI 进程:读环境快照 + 读配置文件 ──► 之后不再重读
  │
  ▼
你今天在同一个窗口里改文件 ──► 运行中的 CLI 一无所知

三层"快照"叠在一起:窗口层(shell 配置)、进程层(环境变量)、应用层(配置文件)。任何一层的修改,都要从那一层往下重新走一遍。

二、三个系统的刷新规则

改了什么macOS / LinuxWindows
shell 配置里的变量source ~/.zshrc 或新开窗口—(见下行)
用户环境变量(setx)—必须新开 PowerShell/CMD 窗口;当前窗口可 $env:名=值 临时补
CLI 配置文件新开 CLI 会话(三家 CLI 通用)
IDE 内嵌终端继承 IDE 主进程环境——重启整个 IDE,重开标签页没用

三、五步排查法(按顺序执行,命中即停)

  1. 同一个窗口里打印变量:echo $MY_KEY(macOS/Linux)/ echo $env:MY_KEY(Windows)。
    打印不出来 → 窗口层问题:变量没写对地方、窗口是旧的。
  2. 确认只有一处定义:grep 一下 shell 配置 + 检查 CLI 自己的配置文件,同名变量两处都在 → 先删一处(单一定义源原则)。
  3. 看进程是否新起:当前 CLI 会话是改配置之前启动的吗?退出重开。
  4. 看文件本身:JSON/TOML 语法错误会让整个配置被忽略或报错——贴进校验器过一遍;.env 检查有没有多余的引号和空格。
  5. 直连上游:用 curl 绕过 CLI 单独测地址和 Key(前几篇都给过命令)——curl 通而 CLI 不通,问题在 CLI 配置;curl 也不通,问题在供应商或网络。

四、为什么这些工具都"只读一次"?

不是偷懒,是稳定:会话进行到一半时配置若能随时变化,同一个会话前后两条请求可能走向不同供应商,计费、上下文、排错全部失控。"启动时定案"是这些 CLI 共同的工程选择。矛盾在于人:人希望"随手一切换",配置却天生静止——这个矛盾,就是下一篇文章(也是本系列收官)的主角。

常见问题

source 之后还是不行?

先确认你改的是当前 shell 实际加载的那个文件:macOS 默认 zsh 读 ~/.zshrc,但如果装过 oh-my-zsh 或改过 shell,情况会变;echo $SHELL 先看看自己用的是谁。

有没有"改了立刻生效"的办法?

对正在运行的会话,没有(原因见第四节)。想接近这种体验,需要"本地代理"类的方案——下一篇讲它的原理。

CI/服务器上为什么更要小心?

CI 每次都是全新进程,反而没有旧快照问题;真正的坑是把 Key 写进仓库或日志。服务器上的长驻进程同理:改完 .env 必须重启服务。
