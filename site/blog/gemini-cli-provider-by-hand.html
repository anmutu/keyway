Gemini CLI 手动换供应商:.env、BASE_URL 与两种认证

博客 · 系列 · 第 4 篇 · 2026-11-06 · 约 6 分钟 · 作者

30 秒答案:Gemini CLI 的供应商配置在 ~/.gemini/.env:写入 GOOGLE_GEMINI_BASE_URL 与 GEMINI_API_KEY 两行;若之前用 Google 账号登录,先用 /auth 切到 API Key 认证;然后重启 gemini 进程——.env 只在启动那一刻被读取,这是它最著名的坑。

二、动手:四步完成

第 1 步 · 编辑(或创建).env

macOSLinux

# 文件不存在就直接创建;已存在先备份: cp ~/.gemini/.env ~/.gemini/.env.bak
cat >> ~/.gemini/.env <<'EOF'
GOOGLE_GEMINI_BASE_URL=https://api.example.com
GEMINI_API_KEY=sk-你的key
EOF

Windows(PowerShell,注意路径在 .gemini 目录)

Add-Content $env:USERPROFILE\.gemini\.env "`nGOOGLE_GEMINI_BASE_URL=https://api.example.com"
Add-Content $env:USERPROFILE\.gemini\.env "GEMINI_API_KEY=sk-你的key"

要点:每行一个 变量=值,等号两边不要加空格,值不要加引号(dotenv 风格)。如果供应商给了带路径的地址,按它的博客原样填。

第 2 步 · 确认认证方式是 API Key

如果你此前用 Google 账号登录过 Gemini CLI,认证方式还是 OAuth——它会无视你的 Key。启动 gemini 后输入 /auth,选择 API Key 方式;这一设置会记入 settings.json,一次即可。

第 3 步 · 重启进程(本篇的灵魂)

Gemini CLI 只在进程启动时读取一次 .env。正在跑的会话不会感知你的修改:退出当前 gemini,重新启动。改完"没反应",99% 是这一步。

第 4 步 · 验证

  1. 新进程里随便问一句,正常回复即通;
  2. 想看变量有没有被读到,可在同一终端先试: 
    grep . ~/.gemini/.env          # 文件内容对不对
curl "$GOOGLE_GEMINI_BASE_URL" -I   # 地址可达性(通则返回 HTTP 状态码)
  3. 报错对照:401/403 = Key 或认证方式错(回看第 2 步);404 = 地址路径不对;模型不存在 = 换成供应商列表里的模型名。

四、三家都看完了:手动切换的全貌

Codex 改 TOML、Claude Code 改 JSON、Gemini 改 dotenv——三家三种格式、三种读取时机,但"换供应商 = 改文件 + 重启会话"的宿命完全一致。下一篇把三家的加载机制拆开讲清楚,解释那个贯穿全系列的疑问:为什么改了配置就是"不生效"?

常见问题

.env 里需要 export 吗?

不需要。dotenv 格式就是 变量=值,加 export 或引号反而可能连字面量一起读进去。

第三方端点必须用 Gemini 格式吗?

是。Gemini CLI 只认 Gemini 格式接口;Anthropic/OpenAI 兼容端点接不进来,选供应商时认准"支持 Gemini CLI/Gemini 格式"。

base_url 需要带版本路径吗?

按供应商博客;Gemini 格式常见的形式是地址直接指向 API 根,路径由 CLI 拼接。404 时先与博客比对路径。
